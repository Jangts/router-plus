# 前端结构规范

本文件约束本项目实际维护的界面组件、文档主题与框架适配展示；结构判断引用这里的编号。源码目录和框架实现以本项目为准，库的算法、协议及服务入口遵守[代码组织与职责](../code-organization.md)，不强制套用页面目录。本文件维护规则，不维护当前文件清单。

## 0. 规则索引

| 编号 | 规则 |
| --- | --- |
| S01 | 结构是变更边界与知识边界的投影 |
| S02 | 一个文件只有一个所有者 |
| S03 | 依赖单向，下层不知道上层 |
| S04 | 先所有者，再职责，再依赖，最后命名 |
| S05 | 公共性由真实消费者决定 |
| S06 | 页面只组合 |
| S07 | 内容与渲染分离，不为“形象”造层 |
| S08 | 第一级按所有者类型收起，组内只放同类 |
| S09 | 归组不是分组；单文件不建归组目录 |
| S10 | 角色目录可以只有一个文件 |
| S11 | 组件目录只放组件、样式和角色子目录 |
| S12 | 非组件文件按角色归位 |
| S13 | UI 契约配置属于组件自身约定 |
| S14 | 全局 hook 与组合 hook 分开放 |
| S15 | 路由层只放纯路由逻辑 |
| S16 | 主题属于 styles，不属于组件或页面骨架 |
| S17 | 名称映射项目已约定概念，不造同义词 |
| S18 | 生成物只由脚本产生 |
| S19 | 结构模型变化先改规范，再改代码 |
| S20 | 局部修正不升级为整体重排 |

## 1. 目的与判据

目录不是文件分类表，而是**变更边界与知识边界的投影**（S01）：谁变化、谁维护、谁可以知道谁。

结构成立的三个判据：

1. 从功能名到改动点，两步内可达。
2. 一次业务改动只落在少数所有者目录。
3. 不读正文，能从目录名与文件自述知道它做什么、归谁。

## 2. 所有者

每个文件只有一个所有者（S02）。所有者是“这个文件变化时，谁必须一起改”，不是文件类型。

| 所有者类型 | 判断 | 例子 |
| --- | --- | --- |
| 业务域 | 有独立页面、数据与交互 | 频道、栏目 |
| 跨域能力 | 被多个业务域消费，有独立生命周期 | 相册、对话、播放、搜索 |
| 基础设施 | 与业务无关的传输、存储、素材、契约 | http、storage、assets、styles |
| 共享展示 | 被多个所有者复用的展示件 | 面板、浮层、控件、图标、表情渲染 |

依赖只能指向更稳定、更无知的一端（S03）。下层不反向知道上层；展示不拥有访问，访问不拥有展示；状态不拥有渲染；规则不拥有副作用。

## 3. 推导顺序

新增功能、移动文件或发现结构问题时，按顺序回答（S04）：

1. 写出变更主体：“当什么变化时，这些代码要改”。
2. 判断所有者类型：业务域、跨域能力、基础设施、共享展示。
3. 判断职责角色：展示、编排、规则、访问、状态、资产、契约。
4. 判断依赖方向：在不知道调用方、当前页面和运行时的情况下能否成立。能就下沉，不能就留在需要这些事实的所有者里。
5. 判断是否新增目录：先放既有角色位置；只有出现第二类长期稳定的职责或生命周期，才增加层级。
6. 命名：目录名表达所有者与职责，不表达当前页面清单、实现形式或临时分类。

禁止反向操作：先决定 `components / services / domain`，再把文件塞进去。

## 4. 第一级与收起

第一级只放职责轴或所有者类型。业务所有者多到难以扫描时，按类型收起（S08）：

- 收起词必须是项目已约定的所有者类型，组内只放同一类。
- 不用同义词、泛称或当前页面清单充当收起词。
- 收起只增加类型边界，不改变组内所有者的独立性。
- 无法归入稳定类型时才留在第一级，并在自述中说明原因。

目录名根据本项目的所有者决定；界面、文档主题与 SDK 适配器分别保留自身边界，不照搬其他应用的目录清单。

## 5. 归组与角色目录

- 归组目录表达“同一所有者、同一变化原因”，至少两个成员；一个文件不建归组目录（S09）。
- 角色目录表达“这是什么职责”，可以只有一个文件（S10）：`hooks/`、`config/`、`context/`、`utils/`、`domain/`、`services/`、`stores/`。
- 没有共同变化原因的同类文件保持平铺，不按数量机械分组。

## 6. 目录准入

目录角色决定能放什么（S11、S12）。

| 目录 | 允许 | 不允许 |
| --- | --- | --- |
| `components/**` 根层 | 框架原生组件文件（如 `.tsx`、`.vue`、Lit 组件 `.ts`）、其样式、`README.md`、角色子目录 | 非组件的逻辑、数据、配置、hook |
| `components/**/hooks/` | 私有 hook | 业务数据、组件 |
| `components/**/config/` | 组件自身契约配置（S13） | 业务配置、运行时状态 |
| `components/**/context/` | 组件组合用 Context | 业务规则、外部访问 |
| `domain/**` | 类型、映射、校验、规则、纯计算、契约薄转出 | 框架运行时／DOM、网络、存储、组件 |
| `services/**` | 外部请求、浏览器能力（存储、剪贴板、媒体、播放安装） | 组件、状态、文案推导 |
| `stores/**` | 跨页面状态 | 单页临时状态、渲染、请求细节 |
| `hooks/**` | 跨组共享 hook（S14） | 组件、业务数据、访问实现 |
| `router/**` | 路由清单、匹配、守卫、导航纯逻辑（S15） | 渲染组件、读取业务状态的组合 hook |
| `workspace/**` | 页面骨架、页面状态、应用级组件 | 具体业务规则；非组件实现留在根层 |
| `ui/**` | 共享展示原语与展示件 | 业务状态、访问层、页面骨架 |
| `styles/**` | 样式、主题令牌、主题适配（S16） | 业务规则 |
| `assets/**` | 素材 | 处理代码、截图、候选稿 |

## 7. 文件类型归位

| 文件内容 | 去处 |
| --- | --- |
| 私有 hook | 所有者 `hooks/` |
| 跨组共享 hook | `hooks/` |
| 读取多个所有者的组合 hook | 组合层 `hooks/`，例如 `workspace/route/hooks/`（S14） |
| 纯数据、映射、消息文案、注册表 | `domain/<所有者>/` |
| 浏览器访问、持久化、媒体能力 | `services/<所有者>/` |
| 跨页面状态 | `stores/<所有者>/` |
| 组件自身允许值、图标清单 | 组件 `config/`（S13） |
| 业务配置、范围清单 | `domain/<所有者>/` |
| 生成文件 | 生成器指定位置，不手改（S18） |

判断不了时先问“它和谁一起变”，再问“删掉它谁会坏”，最后才问“它像什么文件”。

## 8. 命名与概念

项目先有概念，再有目录名（S17）。

- 同一个概念只用一个词；口语说法必须映射到已约定概念。
- 产品结构词可以用作所有者类型名，但必须指向正确层级：频道是一级入口，栏目是频道子页，功能页是辅助页，页面是可路由页，模块是懒加载代码单元。
- 组件目录使用所有者名词；层级位置使用职责词；两者不混用。
- 新增词前先查现有概念表，能映射就不造新词。
- 概念表归属其唯一来源（路由、契约或产品说明），本文件只约定必须映射，不复制当前词表。

## 9. 边界测试

| 问题 | 判断 |
| --- | --- |
| 换一个页面、频道或数据源，它还成立吗？ | 成立 → 公共或能力；不成立 → 当前所有者私有 |
| 它只消费展示数据，还是必须知道分配/状态规则？ | 只消费数据且多消费者 → 共享展示；需要规则 → 留在下层并注入 |
| 它读取状态、路由、网络或页面生命周期吗？ | 读取 → 运行时或访问层；不读取 → 原语或纯规则 |
| 删掉它，谁会坏？ | 坏掉的一方就是所有者 |
| 它和谁一起变？ | 一起变的一方就是邻居 |
| 它的名字能否让你猜到改动位置？ | 不能 → 命名或归属有误 |

## 10. 演进与变更控制

- 新功能先加在既有所有者内，不预建分类（S05）。
- 出现第二个消费者、第二类变化原因或依赖倒置时，才移动或提升。
- 结构模型变化先改本规范，再改代码（S19）。
- 局部修正不升级为整体重排；两个方向都被否定时，停止迁移，回到被否定的具体点（S20）。
- 移动或改名是同一次提交的结构变更：同步引用、自述、README、生成脚本与检查规则。
- 空目录、占位目录、兼容壳、废弃路径直接删除。

## 11. 检查

结构不变量纳入实际检查、类型或相关回归，具体入口见[项目检查入口](../review-entrypoints.md)。本项目未提供的结构检查命令不作为已存在能力，也不为此搬入网站的检查脚本。

检查至少覆盖：

1. 公共层依赖方向。
2. 第一级所有者类型，以及禁止的包装层。
3. 组件目录根层不出现非组件实现。
4. 归组目录不是单文件；角色目录例外。
5. 组合 hook 不在它读取的下层。
6. 主题、生成物、素材位置。

检查脚本里的清单是当前实例，不是规范本身；功能变化时同步实例，规范只在不变量变化时修改。

## 12. 评审

- [ ] 能说出每个改动的唯一所有者。
- [ ] 依赖只指向更无知的一端。
- [ ] 公共性由真实消费者决定，没有预建能力。
- [ ] 目录名能预测内容，没有容器词或包装层冒充所有者。
- [ ] 组件目录根层只有组件与样式。
- [ ] 归组目录至少两个成员；角色目录才允许单文件。
- [ ] 组合 hook 在组合层，全局 hook 在 `hooks/`。
- [ ] 页面只做路由与组合。
- [ ] 空目录、兼容壳、废弃路径已删除。
- [ ] 生成物与自述一致。

## 13. 代码书写

- 分层书写，一屏内可读；不把多语句、表达式或整段参数压成一行。
- 文件头写职责、位置与主要导出；导出函数写入参、返回与异常；类型字段与常量写业务含义。
- 解释性注释按需出现：动机抽象时讲思路，实现繁杂时按步骤解释；不复述代码。
- 注释、目录、自述与 README 链接必须和真实位置一致。
