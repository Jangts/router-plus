# 代码组织与职责

本规范适用于本项目的运行代码、公共包、构建工具及维护脚本。以职责、变化原因和生命周期确定所有者；保留现有框架的扩展机制，不用目录数、类或函数的形式评价组织质量。界面目录的具体规则见[前端结构规范](规范/01-工程目录与协作约定.md)。

## 入口、编排、处理与基础设施

入口负责依赖装配、请求或事件边界和生命周期。编排层直接展示执行阶段、顺序、分支条件、策略、异常去向及结束条件。handler 处理明确业务单元，基础设施提供通用执行机制。每个处理单元能说明输入、输出、前提、副作用和错误归属。

后端分别维护传输适配、校验授权、业务、持久化及外部访问。前端容器负责组合与交互编排，展示、状态生命周期和外部访问具有明确所有者。相同业务的 HTTP、工具或其他入口复用共同规则，保留各入口真实身份与授权边界。

## 集中声明与扩展

稳定可枚举的能力、工具、协议、处理器、状态、路由和策略优先集中登记，直接展示名称、约束、关系及实现入口。同一声明参与装配、校验、匹配和分发；类型检查、启动校验或相关回归保证引用有效，不建立只供模型、程序或文档使用的平行枚举。

静态批量登记使用可独立阅读的类型化配置清单，逻辑引用具名 handler；入口保留依赖注入、顺序、条件、校验与封存。多业务分发按性质采用映射、有优先级的规则、调用链、pipeline、中间件、工作流或组件组合，不强加同一种执行框架。

算法、时序和单条件处理保持合适的过程式表达。首次拒绝、取消、事务、结果提交及错误优先级按原合同保留；声明式组织不能隐藏这些边界。对象无法稳定枚举或清单会明显掩盖算法时，说明有边界的例外依据。

## 目录、共享与依赖

同一能力的说明、脚本和模板按层归于一处。本单包的运行实现归 src/，构建与检查工具归 scripts/，回归归 test/，产品合同归 docs/，长期维护记录归 docs/maintenance/，临时工具与结果归 .tmp/。具有 apps/* 或 packages/* 的工程按对应应用／包边界组织；本项目不为套用目录模板建立空 workspace、部署层或平行工具目录。

跨项目通过声明的包入口或明确的资料输入关系消费，不跨应用相对导入业务实现、不借用其他项目的 node_modules。各项目独立维护依赖锁、素材、产品规则和视觉定义。通用核心不按应用业务名称堆分支，也不反向依赖具体扩展业务。

共享依据真实使用价值与职责完整性，不为凑消费者数量或目录分类制造公共层。相似业务用参数或登记区分，保留有语义差异的生命周期。拆分改善阅读路径，不原样搬走大函数、不制造大量无意义跳转或保留旁路分发。

## 修改与验收

结构或命名调整同步公开入口、调用方、注释、契约、文档、示例和生成来源。临时脚本只放 .tmp，用完删除。正式工具具有文件头职责和关键函数说明；公共包注释使用英文或中英双语。

使用全局技能 `$comprehensive-code-review` 选择适用条目。具体实现与验证见[项目检查入口](review-entrypoints.md)。原有改动、鉴权、取消、事务与数据保留边界保持。执行频率和授权遵守[协作约定](../AGENTS.md)。
