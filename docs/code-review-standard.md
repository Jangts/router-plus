# 代码检查与验收标准

本标准适用于本项目实际存在的应用、公共包、开发工具、文档站及部署配置，用于全量检查、单方面专项检查、修复复查和交付验收。检查同时关注产品符合性、接口设计、代码组织、正确性、安全、性能和稳健性。

以下层级表示审查视角及依赖次序，不要求程序按相同层数拆分。具体产品规则由所属应用拥有；本标准规定如何检查这些规则及判断证据是否充分，不统一各应用的认证强度、使用额度、数据保留期或视觉风格。Agent 分层、数据库、身份、后台任务及界面等条目只在对象具备相应能力时适用，不要求库或文档站补造这些系统。

## 使用方式

1. 按 L0 确定目标、当前合同、范围和执行授权。
2. 全量检查逐层覆盖 L1—L7；专项检查按本文的专项索引选择条目，并追查相关上下游。
3. 每个选中条目记录适用性、源码与调用链、检查方法、实际结果及证据。发现缺陷后，以触发条件、影响和修复后行为复查。
4. 按验收状态出具结论。检查范围、证据范围和结论范围保持一致。

检查条目使用稳定编号，供任务引用。新增条目使用新编号，不因文档排版调整重排已有编号。

| 层级 | 关注的问题 | 主要产出 |
| --- | --- | --- |
| L0 产品与检查基准 | 应当做什么，允许检查到哪里 | 合同、范围、授权与基线 |
| L1 接口设计思路与风格 | 使用者能否容易理解并正确接入 | 接口一致性与使用路径结论 |
| L2 组织、职责与复用 | 规则由谁拥有，入口是否重复实现，前端组件与设计是否一致 | 职责图、注册入口、组件／token／布局关系 |
| L3 逻辑、类型与协议 | 输入如何成为正确结果 | 路径、状态、协议与异常结论 |
| L4 数据、并发与恢复 | 多个操作和失败之后是否仍然正确 | 原子边界、锁、幂等及恢复结论 |
| L5 安全与信任边界 | 不可信数据能否越权或改变执行 | 安全维度与攻击路径结论 |
| L6 资源、性能与稳健性 | 规模、慢请求和故障下能否持续工作 | 预算、性能证据及故障行为 |
| L7 验证、发布与交付 | 证据是否足以支撑验收 | 验证记录、遗留风险与验收状态 |

## L0：产品与检查基准

| 编号 | 检查与通过条件 | 最低证据 |
| --- | --- | --- |
| G01 | 以现行需求、合同和真实消费者确定正确行为。区分公众站点、管理端、专属应用及开发工具的使用场景；安全修复保留已确定的用户体验。 | 产品来源、相关默认值及调用方；说明技术保护与业务政策的归属。 |
| G02 | 明确目标应用、模块、公开入口、内部入口、共享依赖、存储、后台任务和部署边界。全量盘点包含未被测试加载的逻辑模块，不能只检查 Agent 或主流程。 | 范围清单及各入口到共同业务层的映射；明确排除项。 |
| G03 | 保留已有与并行修改，不重置工作区、清库、重建运行初值或修改无关配置。检查区分源码快照、构建产物、锁文件和真实部署状态。 | 检查所用版本或文件指纹、构建来源、并行变更影响。 |
| G04 | 静态审阅、隔离测试、真实模型、真实 OSS、压测及生产操作按任务授权分别执行。文档整理或代码修改不自动扩大为部署、内容维护或外部数据操作。 | 执行范围和数据来源；真实操作有明确目标及最小影响边界。 |
| G05 | 运行频率遵守根协作约定：按明确要求或具体未决疑问选择最小验证；普通小改不自动构建和跑全套。前端视觉预览由用户负责，Agent 查看须有该次明确授权。 | 说明验证解决的具体疑问，记录实际执行内容；未执行项保持未验证。 |

认证方式、默认登录期限、内容可见性、保留政策及正常使用额度属于产品合同。技术风险用后端隔离、约束、恢复等适当机制处理；需要改变产品规则时，应有明确产品决定，不能由审查自行把专属应用改成公众账号体系。

## L1：接口设计思路与风格

详细设计依据为[接口设计规范](interface-design-standard.md)。本层同时检查 API、SDK、配置、回调、工具及流程接口，不能只检查 HTTP 参数。

| 编号 | 检查与通过条件 | 最低证据 |
| --- | --- | --- |
| I01 | 简化来自缺省、复用和稳定引用。封装实际减少使用者必须理解的概念、作出的决定或重复维护的关系；行数、字符数和函数数量不单独代表简单。 | 对同一业务、相同输入和结果比较使用路径，指出省去的具体决定。 |
| I02 | 最小用法是完整用法的子集。增加模型、工具、策略或自定义处理器时沿用同一构造、执行和结果读取方式，不另换 DSL 或调度机制。 | 从最小示例逐步增加需求的连续示例。 |
| I03 | 固定配置、默认依赖及一对一关系由实例绑定；集合通过登记管理。身份、取消信号、额度和请求状态保持本次运行作用域，不能固化进共享定义。 | 构造／绑定／登记／单次调用的参数归属及共享实例用例。 |
| I04 | 同组接口统一术语、命名、参数方向、可选项位置、路径语法、单位及返回关系。实体 ID、定义身份、运行身份、显示名称、来源状态、版本与修订分别表达。 | 同组接口对照和真实调用方；外部 wire 字段由适配器保持其标准语义。 |
| I05 | 默认值有明确含义、优先级、作用域和覆盖方式。`0`、空字符串、`undefined`、空集合、未处理及失败按合同区分，不统一解释成“没有值”。 | 缺省、显式空值、精确覆盖和冲突配置的边界用例。 |
| I06 | 便利输入仍返回同一种结果合同；局部值、流程结果、调用回执及错误各有明确语义。同步入口拒绝异步结果，异步入口等待真实完成。 | 短写／完整写法的同形结果；thenable、合法 `undefined` 及 handled/unhandled 用例。 |
| I07 | 普通对象、自定义实例和推荐实现按同一接口工作。保留方法接收者、原型方法及合法 getter；复制、冻结或序列化只发生在合同规定的边界，不误处理 App 服务实例。 | 原型、私有状态、getter、快照／只读／共享关系的用例。 |
| I08 | Core 定义双向接口与运行保证；Support 在 App 侧辅助接入和补全；Kit 拥有可选的局部业务协议。Core 不依赖 Support／Kit 的业务名称、状态或必选启动过程。 | 依赖方向与实际导入；自定义实现、推荐实现使用同一 Core 合同。 |
| I09 | Core 基础缺省与 Support 场景补全分别有依据。策略档位公开映射、适用条件、成本和覆盖方式，保留自定义 handler 及精确参数。没有依据时不承诺“最佳”、速度或质量。 | 默认实现与场景策略的来源、映射及覆盖用例。 |
| I10 | 公共执行规则适用于手写配置与生成器产物；生成器专属命名习惯和默认策略由生成器拥有。不在通用层增加用于识别某个 helper 的标志或重复可推导字段。 | 手写配置与生成配置的等效执行；公共规则的实际所有者。 |
| I11 | 公开面有明确职责，聚合入口和子入口转出同一实现。避免同义别名、无职责转发及平行执行路径；按已确定的兼容合同处理迁移，不为开发期旧写法无限增加兼容层。 | exports、公开类型、示例、开发脚本与全部消费者的一致性核对。 |
| I12 | 执行身份、模型／工具调用、子调用、观察及持久记录能关联到真实调用。预览、局部结果和日志投影不冒充最终验证或额外副作用。 | 一次真实执行的身份链、回执与观察事件对照。 |
| I13 | 已知实体、传输及 schema 关系保留类型推断和结果收窄；动态输入保持 unknown 并经解析确认。登记查询的返回类型对应实际投影，不能把部分字段强转成完整实例。 | 公开入口的正反类型用例、动态输入解析及登记查询的实际值。 |

接口风格统一以降低误用和学习成本为目的。形式一致不能放宽授权、预算、取消、持久化、完整响应及交付合同；同组接口允许有明确语义依据的差异，不为整齐增加概念。

## L2：组织、职责与复用

| 编号 | 检查与通过条件 | 最低证据 |
| --- | --- | --- |
| A01 | 入口负责装配、传输边界和生命周期；编排说明阶段、顺序、分支、异常及结束；handler 处理明确业务单元；基础设施拥有通用执行机制。每个单元能说明输入、输出、前提、副作用及错误归属。 | 从入口到校验、授权、业务、持久化、外部调用的职责图。 |
| A02 | API、Agent node/tool、后台任务等对同一业务使用共同规则和业务处理路径；适配层保留各自传输、交互和授权入口，不重复另一套直写、可见性、检索或引用维护。 | 同一业务从各入口进入共同实现的调用链与行为对照。 |
| A03 | 可稳定枚举的能力、意图、工具、协议、路由、状态和策略优先集中声明并实际驱动执行。启动校验、类型检查或相关回归保证引用有效。 | 声明入口及装配、校验、匹配、分发的消费者；清单与实现对应关系。 |
| A04 | 多业务分发使用映射或有优先级的规则清单；算法、时序和单条件处理保留合适的过程式表达。拒绝检查保持职责分组、首次拒绝顺序和诊断标签。 | 关键分发及拒绝路径对照；组织方式与行为等效分别复核。 |
| A05 | 拆分改善职责和阅读路径，不能把大函数原样搬家、制造小函数跳转链，或在清单外保留平行分发。静态登记采用可独立阅读的类型化清单，逻辑引用具名 handler。 | 模块入口、处理单元职责与复杂分支的阅读检查。 |
| A06 | 按 workspace 和公共包边界复用。应用显式声明依赖，不跨应用相对导入实现或借用别端 node_modules；通用工具按职责完整性判断是否成包。 | 依赖声明、包清单、导入图与公开导出。 |
| A07 | 消费者按所需能力使用公开入口。浏览器依赖图不意外带入 Node、原生库或无关 Core 运行模块；ESM、CommonJS 和浏览器条件按实际承诺检查。 | 实际导入链、公开解析及必要的构建产物证据。 |
| A08 | 前端容器负责组合与交互编排，组件、状态生命周期和外部访问职责明确。宽度、滚动、对齐、表面、间距、状态及脱流占位各有所有者；各端视觉定义独立。 | 组件与共享消费者的源码核对；视觉结果由本次授权的验收方确认。 |
| A09 | 文件按类型、模块和层级分目录组织，不把多类职责散铺在同一层级或塞进单一文件；目录边界与职责边界一致，新增文件落入已确定的归属，不随意新建平行目录。 | 目录树与模块职责对照，同类文件的统一落位及各目录的归属说明。 |
| A10 | 相似业务抽象为公共实现，用参数或登记区分变体；不靠复制粘贴后改几行来派生，不用私有成员、私有属性或平行文件仅作区隔而掩盖本可参数化的重复。 | 相似实现的并排对照、公共实现的参数或登记点、其全部消费者及复制粘贴的替代依据。 |

采用对象、类或函数均可。结构优化按职责、复用和可读性验收，不以某一种编程范式作为质量标准。详见[协作约定](../AGENTS.md)、[Workspace 结构](workspace.md)、[代码组织与职责](code-organization.md)和[项目检查入口](review-entrypoints.md)。

### L2.1：前端设计风格与布局一致性

本专项检查同一应用内部的设计语言及其代码实现。全局配色与尺寸 token 指该应用自己的全局定义；各界面项目分别维护视觉规范，共享浏览器及控件 reset 不意味着共享色值、尺寸或材质。本标准不指定具体配色、字号、间距或断点数值。

| 编号 | 检查与通过条件 | 最低证据 |
| --- | --- | --- |
| U01 | 能定位该端现行设计来源及主题入口；同类页面、区域和控件使用一致的视觉角色与规则。既定例外有明确用途，不把页面偶然写法当作另一套标准。 | 该端设计文档、主题／样式入口、页面及组件分类对照。 |
| U02 | 配色使用该端全局语义 token 表达文字、表面、边界、强调及反馈等角色，基础色与语义映射归属明确。组件库主题、CSS及Portal共同消费适用主题，避免同一角色散落独立色值或失去主题上下文。 | token定义、组件库映射、主题切换及代表性消费者核对。 |
| U03 | 字体、字号、行高、间距、控件尺寸、圆角、层级及动效等可复用数值由该端 token 或集中规则管理。组件默认值与变体来源清楚，局部数值服务真实特例，避免任意微调累积成多套尺寸体系。 | 尺寸与排版来源、公共控件和页面使用对照；例外说明。 |
| U04 | 通用页框、内容区、卡片、表单、列表、标题栏及常用控件按该端实际职责复用；页面负责组合和声明用途。公共能力通过组件或参数提供，不依靠页面私有CSS反复修补同一个公共组件。 | 组件树、变体及消费者清单；重复结构和私有覆写核对。 |
| U05 | 同一视觉角色在相同容器中保持统一的宽度、边距、网格及对齐基线。核对标题与正文、表头与单元格、标签与输入框、图标与文字、按钮组及页头／页尾，不仅检查单一元素的坐标。 | 对齐所有者和关联元素范围；相应状态与尺寸下的视觉结果。 |
| U06 | 宽度、滚动、对齐、表面、间距、状态及脱流占位各有明确所有者。外层页框、内层内容和业务子组件职责可追踪，避免重复背景、双重卡片、层层padding和相互抵消的尺寸计算。 | 内外容器层级图及各职责的唯一所有者；真实页面消费者。 |
| U07 | 每个滚动轴及独立窗格有明确滚动容器、尺寸约束和事件归属；body、页面、面板与列表不意外争抢同一滚动职责。合理保留多窗格滚动，核对滚动链、滚动条、锚点、恢复位置和虚拟列表使用的真实容器。 | 容器高度／flex约束、overflow及滚动事件链；滚动与恢复结果。 |
| U08 | 公共内边距由真正拥有该间距的容器维护。需要全宽子项时明确其内外层边界，不能为一个子项取消全部共享间距，再让每个页面补回；不以任意margin或负偏移掩盖父层职责问题。 | 同一容器全部直接子项的范围，以及内缩／全宽两类关系。 |
| U09 | 固定、粘性、浮层、抽屉、弹窗及Portal的定位、层级、主题和占位有归属；脱流后保留正确内容空间，避免盖住正文、输入区、菜单和滚动条。 | 定位包含块、层级来源、占位与可滚动区域对照。 |
| U10 | 按该端声明的宽高范围、断点和主题检查布局；窄屏、短视口、长文本及不同内容量不造成非预期裁剪、溢出、错位或双滚动。不能为优化一个页面破坏共享布局，也不能据局部结果扩大产品适配承诺。 | 适用视口／主题／内容量矩阵及各公共布局消费者。 |
| U11 | 普通、悬停、焦点、选中、禁用、加载、空、错误及成功等适用状态的样式与语义一致。优先复用本端控件和图标入口，浏览器基线归统一reset；不在各页面重复修补组件库默认效果。 | 控件状态矩阵、交互语义、token与reset实际来源。 |
| U12 | 公共样式、布局及控件修改覆盖其全部消费者；源码结构、token引用、视觉对齐与真实滚动交互分别验收。静态检查不能证明最终像素或外观一致。 | 消费者／断点／主题／状态清单；源码核对与人工视觉结果分别记录。 |

设计一致性、功能正确性和渲染性能分别出具结论。视觉查看遵守G05：没有该次授权时由用户验收，未取得的视觉证据记为未验证。曾经查看过少量页面、测过帧间隔或通过组件测试，不能据此认定已完成全部设计一致性检查。

### L2.2：代码风格与可读性

本节检查源码的可读性约定：格式化与注释以“人读得懂、能定位故障”为目标，不规定具体业务或视觉数值。格式化由统一工具与配置维护，注释遵循本项目语言约定（公共包使用英文或中英双语）并紧贴代码，不另立单独 API 文档替代编写；未按配置落盘的手写堆叠、缺失的自述或只复述代码表意的注释均属缺陷。

| 编号 | 检查与通过条件 | 最低证据 |
| --- | --- | --- |

## L6：资源、性能与稳健性

性能检查覆盖前端请求与资源、界面渲染、后端请求与存储、公共包算法及整条交互链。适用项按真实功能选择；前端打包变小、后端回归通过或单段算法变快，不能互相替代验收。

开发环境不运行压测；生产模式、隔离数据库和本机回环端口不构成例外。压测仅在稳定、可控、可重复的专用测试环境执行，并依据实际访问量、目标用户和容量需求确定负载与指标。代码检查不自动包含压测。性能优化应由具体设计、算法、重复工作等代码证据或可靠的前后对照支撑；并发正确性测试不提供容量证据。一旦确认环境或数据不可靠，立即停止测量及由其驱动的优化支线，记录无法确定，不靠追加轮数、剖析或微基准延长追查。

| R15 | 图片、头像、动画帧、Canvas、播放器及文档预览复用适用的下载、解码和派生产物；避免每帧或每次挂载重新加载／解码／建Canvas。离屏、隐藏、切换及卸载后正确暂停或释放，缓存保持有界。 | 首次与重复显示的请求、解码、帧生成和实例次数；多轮切换后的内存及资源趋势。 |
| R16 | 按G05授权进行真实浏览器采样时，覆盖加载、交互、滚动、流式更新及反复导航，记录首屏可用、交互响应、长任务、帧间隔、布局偏移和内存等适用指标。rAF频率不直接等同GPU呈现帧率或所有设备流畅度。 | 浏览器／设备／视口／网络／缓存条件、操作路径、采样时长和原始指标；与源码、功能及视觉结论分别记录。 |

| --- | --- | --- |
| R17 | 分解请求排队、解析、认证授权、业务、数据库、外部I/O、序列化及发送耗时。排查事件循环上的大段同步工作、长临界区和CPU密集任务；优化后保留完整请求与错误语义。 | 阶段耗时、CPU profile、事件循环延迟及并发下的尾延迟；定位实际热点。 |

| R22 | 缓存策略明确请求级、会话／用户级、进程级、持久索引及HTTP／CDN等适用层次；声明键、权限作用域、版本、容量、TTL、淘汰、失败值及过期策略。选择回源、写后失效或同步更新等适用方式，异步回写另有持久化保证；不同用户资料、过期授权或可变资源不错误共用。 | 缓存设计表及命中／未命中／冷暖对照；跨用户、权限、参数、语言或版本隔离的适用用例。 |
| R23 | 数据变更、删除、发布、账号切换及版本变化后，缓存和派生索引按合同失效、更新或重建；并发未命中可适度合并，防止热点击穿、穿透、集中失效或无界增长。允许陈旧值的范围须由业务决定，故障降级不绕过权限或丢失源数据。 | 缓存失效、并发回源、删除后重访、重建、故障恢复及容量上界用例；陈旧值和来源重读核对。 |
| R24 | 服务压测覆盖读写比例、数据规模、并发阶梯、热点／锁竞争、长连接／SSE、慢消费者、取消及故障恢复等适用场景。分别报告正常成功、预期业务拒绝和非预期错误，拒绝请求的高吞吐不冒充成功业务容量。 | 生产模式隔离负载记录；p50／p95及适用分位、吞吐、状态码、CPU、RSS、事件循环、连接／活动流与结束后的状态。 |

## L7：验证、发布与交付

### 验证要求

| 编号 | 检查与通过条件 | 最低证据 |
| --- | --- | --- |
| V01 | 检查条目可追溯到实际逻辑和证据。修复验证行为与原因，不只验证代码行被执行；测试保持既有校验、错误语义及产品边界。 | 条目／入口／分支／用例映射，必要的故障负例与回归。 |
| V02 | 覆盖率报告包含范围内全部生产逻辑模块，包括未加载模块；区分行、分支和函数，标明分母、工具、构建及源码映射。编译辅助代码的排除有依据。 | 完整范围与未覆盖列表；要求全分支时逐项闭合业务分支，未达到不能标记完成。 |
| V03 | 静态推理、类型检查、单测、集成、真实协议、真实模型／OSS、负载、长期内存及故障恢复分别提供对应证据。隔离转译不冒充类型检查，假执行器不证明真实进程行为。 | 验证层次、运行对象、mock边界、样本与环境；未执行的层次明确列出。 |
| V04 | 实际消费正确构建产物，检查安装锁、条件导出、跨平台可选包、生成来源、配置默认值及镜像复制范围。共享 dist 的构建与读取有协调，受干扰结果作废后按影响范围重跑。 | 生产导入／安装预演、构建来源与生成一致性；部署时核对真实环境覆盖值。 |
| V05 | 真实测试优先使用隔离环境和合成数据；外部操作限定明确对象与清理范围，保留真实回执。测试不误删用户数据、共享 OSS、备份或内建保护，不以清库和 seed 解决问题。 | 测试对象身份、环境、隔离方式及可核对的清理结果。 |
| V06 | 实现、Markdown、契约、示例、Skill、开发脚本与网站来源同步；生成内容从来源更新。已确定的设计写入正式文档，审查过程及一次性证据按各自用途保存。 | 真实消费者和文档链接核对；交付说明列出改动、理由、验证及边界。 |
| V07 | 发现、修复、复查分别有记录。修复后复查共同处理路径、其他消费者及可能回归的边界；任务允许协作时可以分工与交叉审阅，结论仍核对实际改动和证据。 | 原触发条件已闭合、相邻路径未回归；协作结论有共同基线，不能只汇总“已完成”消息。 |
| V08 | 公开包 README 能引导首次安装、接线、运行和继续使用；description／keywords 与实际用途和搜索词匹配。保留已完善文档结构，按[公开包文档检查](documentation-standard.md#公开包的使用入口与发布检查)核对最终 tarball，发布后核对公共 README 与元数据。 | 示例、运行前提、结果与文档入口的实质复核；实际包体与 registry 证据，明确离线、类型或真实服务验证范围。 |

测试不得通过以下方式制造通过结果：删除守卫、放宽权限、缩小统计范围、排除未加载业务模块、把编译器分支当业务覆盖、mock掉被测规则、把错误行为改成期望结果，或只运行证明缺陷仍存在的探针。

全量检查以覆盖范围内全部业务逻辑为目标；任务要求全分支覆盖时，未覆盖分支必须继续验证、证明不可达或说明合理排除依据。专项检查按其合同和风险确定充分证据，不凭空指定统一覆盖率门槛。测试全部通过、高覆盖率及依赖零告警各自说明一类证据，均不单独等于全量验收通过。

### 检查与验收状态

| 状态 | 使用条件 |
| --- | --- |
| 通过 | 适用合同明确，所需检查和证据充分，结果满足该条目的通过条件。 |
| 不通过 | 有可复现缺陷、可达违反合同的路径或确定的不满足项。说明触发条件和影响。 |
| 未验证 | 证据、环境或执行范围不足。静态推导、可达性待核实和真实环境未测分别说明。 |
| 不适用 | 该对象没有对应能力或风险面，并能说明依据；不能用于掩盖未检查的模块。 |

发现项分别标记证据性质：已复现、源码确认、依赖公告命中、条件性推导。严重性结合可达性、权限前提、数据影响及恢复成本判断，不能把所有公告条目都计成独立可利用漏洞。

选中条目存在未关闭的不通过，或缺少任务要求的验证时，整体结论不能写成验收通过。已执行全量盘点但存在覆盖或环境缺口，可报告检查范围和实际结果，不宣称所有逻辑、所有分支或整个系统已被证明安全。

| 测试与覆盖完整性 | V01—V07 | 全部分母、真实构建、mock边界、负例、覆盖缺口与结果有效性。 |
