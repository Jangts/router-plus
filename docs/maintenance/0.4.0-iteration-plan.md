# Router Plus 0.4.0 优化与扩展迭代计划

后续结果：S1—S6 已实施，用户另行授权的 0.4.0 公共 npm 发布已完成，见[发布记录](0.4.0-release-2026-11-12.md)。以下保留计划及发布前阶段状态。

日期：2026-11-12。状态：选定范围 S1—S5 已实施；用户追加的来源事件与顺序编组统一纳入未发布的 0.4.0，见下文 S6 及[实施与验收记录](0.4.0-implementation-acceptance-2026-11-12.md)。以下保留计划形成时的分析与阶段目标；第 7 节仍为暂缓候选，不属于本次交付。包版本保持 0.3.1，变更记入 0.4.0 Unreleased，尚未升版或发布。本文不构成已发布 API 合同，不授权部署或迁移消费者。

## 1. 版本目标

建议下一功能版本为 **0.4.0：稳定原生接入，改善外部访问与诊断**。保持原生参数／返回值、可选最后一个 idOrOptions、同一创建与登记路径，以及原生来源唯一持有实时状态的原则。

版本成功的标准是接入与排障更简单，内部生命周期更容易验证，而不是公开方法更多。已确认的正确性缺陷如果可以独立兼容修复，可先作为 0.3.2 维护版本处理，无须等待 0.4.0。

计划形成时以 0.3.1 的 155 项通过记录作为历史基线，仅做源码分析。实施后的实际验证、复现与限制独立记入实施与验收记录，不将最初的风险推断等同于已复现缺陷。

## 2. 现状与机会

| 方向 | 源码证据 | 问题性质与建议 |
| --- | --- | --- |
| Core 编排 | `src/core/router.ts` 同时拥有导航、来源登记、恢复任务、scope 门面和清理；`bindingBatch` 延迟执行 effect，每个来源仍可分别安排 applyLocation／restore。 | 维护复杂度与重复工作的明确候选；尚无性能收益测量。按真实职责收敛登记与恢复编排，不搬运大函数或引入通用工作流。 |
| React 提交边界 | `react/existing-state.ts` 已隔离废弃 render；`react/boundary.ts` 的 RetainedOutlet 仍在 render 中修改 entries.current，RouterPlusRetained 在 render 中写 frozen.current。 | 存在需要复现的并发风险，不能据此宣称线上已发生缓存污染。优先覆盖 Suspense／中止 render 下的保留视图。 |
| 来源能力切换 | `useReactState` 在 commit 发布来源，在 passive effect 清理／重建登记；bridge 的读写引用 committed.current。 | 需覆盖 ID、owner、读写／调用能力切换时的 layout→passive 间隙，确认旧 ID 不误用新来源。 |
| 状态元数据 | 当前有 listStateKeys、getState、callState 和错误回执；没有统一公开接口描述一个 ID 是否可写、可调用、绑定哪些 QS 参数。 | 外部工具需通过尝试操作判断能力。适合增加只读的来源描述入口，而不是再建一套状态。 |
| 类型投影 | `stores/native.ts:dataValues<S>` 删除函数字段但返回类型仍为 S；Redux 创建器使用 Creator/ReturnType 组合与内部 any。 | 运行时数据投影与类型边界值得收紧。需保持原生 store 返回类型，不靠调用方补泛型掩盖推断缺口。 |
| QS 分类与恢复 | `native-bindings.ts` 用 util.isPlainObject 选择 decode 归属，`state-fields.ts` 用更严格的 isQueryObject 判定普通对象；每次计算 rules／queryKeys。 | 分类依据不完全一致；需要覆盖 Date／Map／Set、自定义实例及 codec 的测试后收敛。缓存仅适用于已固定的规则，不能缓存实时值。 |
| 诊断 | router 中既有隔离诊断 sink 异常的 bindingDiagnostic，也有直接调用 onDiagnostic 的路径。 | 需验证诊断回调抛错是否改变命令／清理结果，统一异常出口；扩展结构化信息时保持现有回调兼容。 |
| 包交付 | finalize 脚本负责 ESM 标记和 CSS，没有清除过期编译文件；已有发布包包含已改名的 page-tab 编译残留。 | 清洁构建与增量构建可能产生不同文件集合。旧文件无公开 export，不等于仍支持旧接口；应保证产物可重复。 |
| 兼容验证 | 0.3.1 发布记录只验证了当时安装的一组 React/Vue/Store 版本；peer 范围更广。 | 当前证据不覆盖全部声明范围。建立有限、明确的兼容矩阵，而非把一组测试扩大为全版本保证。 |

## 3. 固定设计边界

- `useRp*` 继续作为创建入口；已有来源通过 useReactState／useVueState 接入，省略配置不登记。普通接入不增加必填项。
- Vue Options API 继续使用 setup；setup store 直接使用同一套 composables，不新增组件 bind/unbind 或 Vue Store 包装体系。
- React 的三种 Store 创建包装与已有来源登记继续共用实现。Redux 业务 setter、Jotai 原生命令／完整值赋值的区分保持不变。
- Tab 仍是普通状态；不恢复 Tab 专用状态模型。RP 不提供页面使用的全局 Store。
- QS 保持整组与字段 encode/decode、非标量字段默认 JSON、明确参数归属和无关参数／hash 保留。不增加自动递归展开、隐式动态参数或新的配置 DSL。
- 业务校验、权限、冲突处理、草稿保存仍由原生来源持有。取消不承诺撤回已经发出的业务副作用。

## 4. P0：先收敛正确性与生命周期

### A. React 保留视图与登记切换

涉及 `react/boundary.ts`、`react/provider.ts`、`react/existing-state.ts`，必要时追踪 Core scope。

先增加能够区分已提交／废弃候选的用例：保留 A，向 B 发起会 suspend 的 transition，然后取消；在导航与布局 effect 期间读取 A 的状态、原生 location、callback 和 host。同步覆盖同一 Hook 的 ID、Provider／owner、readonly↔writable、callback↔accessor 切换。

若复现泄漏，render 只构造候选，缓存和活跃桥只发布提交结果；原生值的直接可见性与 RP 登记生命周期分别处理。不能以频繁重登记所有来源作为修复，也不能破坏首次 QS 恢复、Strict Mode 或 hidden scope。

**验收：**废弃 render 不留下缓存／scope／订阅，不改变已提交闭包；旧 ID 不调用新来源；切换回原页面时来源、DOM 与原生路由上下文一致。未复现的路径保留测试证据，不为假设改动机制。

### B. 来源元数据与异步恢复

覆盖同一 pageId 的多个 retained instance，分别登记同名来源；按不同顺序卸载／重挂，确认页面级导航规则不会随某个实例退出而丢失或残留。区分静态目录声明、动态规则与实例来源，不直接把它们合并成第二个 Store。

扩展晚到成功／失败、替换、dispose、订阅与清理抛错的交错矩阵，重点检查初始恢复、whenReady、并发 setState 和自定义 codec。约束为：一次操作只对其捕获的来源身份结算；旧任务不能污染新来源的恢复结果。

**验收：**逐项保持 0.3.1 的原子回滚、幂等注销、真实提交事实及取消合同。若发现行为缺陷，先形成最小复现再修复。

### C. 诊断失败隔离

统一内部诊断调用入口，保留 onDiagnostic(error, stage) 的使用方式与原始错误。诊断回调自身失败不得阻断剩余清理、使已提交回执伪装成未提交，或掩盖主异常。

结构化的 sourceId、scope、阶段等信息先在内部组织；若确需公开扩展，采用兼容的可选上下文参数并同步类型、示例、隐私边界。不记录实时状态、调用参数或 codec 原文作为默认诊断内容。

## 5. P1：内部优化与类型准确性

### D. 合并登记与恢复编排

在现有 binding host 上实现同一显式登记批次内的恢复去重：先建立完整索引与规则，再按实例安排必要的地址重建／恢复。维护明确的回滚、观察和恢复顺序。

只合并确定等价的工作。不能跨业务 await 隐式合并命令、丢掉中间导航回执，或把不同 scope、不同地址快照的恢复任务错误合并。Core 仍不导入框架或 Store 类型。

可将来源登记／规则归属及恢复调度拆成有独立责任的内部模块，保留 RouterPlusImpl 负责装配与导航编排。不以函数行数或目录数量作为完成标准。

**验收：**用确定性测试统计一次批次的地址构造／恢复次数，证明减少重复工作；同时证明首次恢复、即时订阅、重入登记、失败回滚和 whenReady 等待边界不变。该证据不当作吞吐提升结论。

### E. 固定规则的预计算与数据投影

预计算固定登记生命周期内的 queryKeys、字段规则、参数归属及默认编码分类。规则变化随新登记／元数据修订失效，不能仅用 PageDefinition 对象身份缓存，因为动态 states 会改变。继续在每次操作读取原生当前值，保留 codec／校验回调的实际语义。

Zustand 数据投影可评估复用相同原生 state 引用的结果，但要先确认原地修改／中间件路径；不得把它写成对所有 Store 可靠的假设。没有完整失效依据时保留现有实现。

### F. 原生泛型与索引类型

先完善类型消费者用例，再调整签名：

- Zustand：索引的数据字段类型排除动作；原生 store 仍保留全部方法及 middleware 能力。
- Redux：验证 reducer map、createSlice、middleware 扩展 dispatch、preloadedState 和增强器；避免包装后退化成 any 或丢失原生 dispatch 类型。
- Jotai：保持只读、primitive、自定义 write、多参数及异步结果的区别；不通过重载回退绕过 readonly 限制。
- Vue：覆盖读写类型不同的 writable computed、readonly proxy、容器与访问器；完整值恢复能力不靠 setter 存在就猜测。
- QS：普通对象组与非普通对象 codec 的类型和实际 encode/decode 输入保持一致。

**验收：**NodeNext ESM／CJS 正反类型用例覆盖以上场景，错误调用不能通过 any 或宽泛重载悄悄通过。不得为动态字符串 ID 伪造全局静态参数／返回值保证。

## 6. P1 扩展候选：来源能力查询

建议将“外部可发现性”作为本版唯一新增公开能力。拟议入口：

```ts
plus.inspectState();         // 当前 facade 可访问的来源描述
plus.inspectState('filter'); // 单来源描述；未知来源返回 null
```

拟议描述包含稳定 ID、作用域身份、read/write/call 能力、已声明 QS 参数名，以及动作的父来源关系。只描述登记事实，不执行 getter、codec 或命令，也不返回实时值、原生对象、函数引用和业务参数。

实现必须读取现有登记结果，不维护平行能力表。主来源／动作整组成功后才可见，失败回滚及 stop 后立即消失。静态页面地址声明与已挂载的实时来源必须区分，不能把一个尚未挂载的 states 声明报告为可写来源。

**进入实现前收敛：**返回对象的字段名、列表范围、父来源关系及 facade 行为；字段路径是已声明字段还是动态读取路径，必须明确。第一版建议不展开任意对象字段，避免读取来源和制造无限目录。上述名称与形状为提案，不写入当前正式 API 文档。

**验收：**外部调用者能先判断是否可调用／可写；查询无业务副作用、不泄露值；全局与页面同名、隐藏实例、未知 ID、dispose 和聚合注销均有一致结果。全局调试门面是否暴露此入口需显式决定，不自动扩大。

## 7. 后续扩展池：暂不进入交付承诺

| 候选 | 收益 | 暂缓原因与进入条件 |
| --- | --- | --- |
| 具有类型的状态／命令 handle | 本地调用保留值、参数元组与返回类型，减少字符串错误。 | 不能替代动态 ID，也不能增加“创建—登记—取 handle”必经步骤。等待能力查询落地及真实消费者证明需要。 |
| Store selector／通知过滤 | 大 Store 下减少无关投影和通知。 | 字段路径、动作和 QS 恢复需要共享同一投影；需真实接入案例，不能仅增加一个看似方便的 select 配置。 |
| QS 输入频率控制 | 连续输入时减少地址提交。 | 防抖会改变历史、取消、回执与离开时 flush 语义。先验证现有并发写入是否足够，不默认每个 binding 加计时器。 |
| 可选业务调用 AbortSignal | 业务操作可以主动停止正在进行的任务。 | 自动在原参数后追加 signal 会破坏“原参数一致”；需要可选适配合同及真实可取消来源，不宣称停止原生副作用。 |
| 导览可访问性和文案配置 | 可定制按钮语言及键盘／读屏行为。 | App 自定义 renderer 已存在。先识别默认组件的实际缺口，避免同时加入翻译、焦点陷阱和通用 UI 框架。视觉验收仍归用户。 |
| 调试面板／更多 Store 适配 | 提供直观开发辅助或覆盖其他生态。 | 元数据查询可以先支撑外部工具；没有消费者证据时不新增 UI 面板、MobX 包装或恢复 Vuex/Pinia 专用公开入口。 |

## 8. 交付质量与兼容矩阵

### 构建与包体

清理本包明确拥有的编译输出后构建，或从源码清单生成准确产物集合；不清理其他包、应用及用户目录。清洁构建／增量构建应产出相同的发布文件集合。打包回归增加对过期模块、未声明入口和内部产物的检查，不能只比较 ESM/CJS 的导出名称。

从实际 tarball 在隔离消费者中核对 import／require／类型／CSS 和可选 peer 隔离，保持 README 的相对链接可用。站点 API 继续由源码及统一编排生成，新增入口不能只补生成页。

### 兼容验证

分层运行 Core 无框架、React、Vue、各 Store 三类组合，先选能覆盖声明下限和当前开发组合的有限矩阵。具体版本以实施时选定并验证的依赖为准；本计划不依赖对“最新版本”的猜测。隔离依赖不得写入应用目录或替换根锁文件。

若声明下限不通过：先判断实现缺陷还是使用了高于下限的 API，再决定修复或调整声明；不能静默缩小 peer 范围。避免穷举所有笛卡尔组合。

## 9. 实施顺序与阶段门槛

| 阶段 | 任务 | 产出与结束条件 |
| --- | --- | --- |
| S1 正确性 | A、B、C | 最小复现与修复记录；诊断、取消和恢复合同收敛。独立修复可评估维护版。 |
| S2 内部收敛 | D、E | 单一路径的登记／恢复编排；固定规则预计算；用次数断言证明去重，无行为回退。 |
| S3 类型与交付 | F、清洁构建、有限兼容矩阵 | 正反类型与实际 tarball 消费者通过；原生返回身份不变。 |

| S5 验收 | 汇总回归与文档审校 | 记录实际通过项、已知限制及兼容组合；另行取得发布指令后升版／发布。 |

阶段验收不按新增测试数量定指标。使用历史 155 项回归作为保留行为基线，再增加能区分具体失败／修复结果的用例；不为实现细节复制测试。构建集中在接线完成和必要修复后，不逐函数重复执行。

计划形成时只写入 maintenance。经用户授权实施后，已同步源码、README、正式合同、双语网站来源和生成页；包版本及已发布 0.3.1 保持不变。S4 的 inspectState 已纳入实现；实时值缓存、新诊断参数及第 7 节扩展池未纳入。

## 10. S6：来源事件与依赖命令编组

用户确认继续迭代后，此项直接归入尚未发布的 0.4.0，不拆为 0.4.1。

- 注册／注销／框架提交通过统一 subscribe 发送 state.registered、state.unregistered、state.committed，沿用现有来源索引与 StateInspection；disposed 负责通知等待者终止。
- execute 支持现有命令数组及整组 timeoutMs／signal，单命令行为保留。依次等待指定来源、初始化恢复和适配器提交后执行，不引入 Panel／Form 专用模型或新的流程 DSL。
- 显式导航后选择实际目标实例；离开、释放、销毁、执行中来源替换、失败、超时或取消停止后续步骤。已完成回执保留，不回滚或重放业务操作。
- 覆盖 React／Vue 条件挂载、最新提交闭包、整组回滚、源码身份替换、作用域主动导航和导航后处理期间离页。框架提交不等同于业务数据加载完成；应用仍拥有异步初始化及实际副作用。

实现、文档与实际验证记录统一在实施与验收记录的 S6 小节维护。
