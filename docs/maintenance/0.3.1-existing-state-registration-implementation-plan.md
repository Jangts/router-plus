# Router Plus 0.3.1：已有状态登记评估与落地方案

日期：2026-11-12。状态：S1—S6 已实施，实际检查见[验证记录](0.3.1-existing-state-registration-acceptance-2026-11-12.md)。

输入为 [原始提案](0.3.1-existing-state-registration-proposal.md)，源码基线为当前工作目录中的 0.3.0。本文保留实施设计与范围，当前使用合同见 [Native state bindings](../../packages/router-plus/docs/state-bindings.md)，执行证据见独立验证记录。

## 1. 评估结论

建议纳入 0.3.1。新增能力是复用已存在的来源，补齐创建包装器之外的接入路径；已有创建 API 继续作为更省事的入口。两种入口必须落到同一个登记实现，不能增加第二套状态、分发或订阅机制。

保留提案的五个公开入口，不增加别名：

| 子路径 | 入口 | 返回值与生命周期 |
| --- | --- | --- |
| `/vue` | `useVueState(source, idOrOptions?)` | `void`，随组件／store effect scope 注销 |
| `/react` | `useReactState(source, idOrOptions?)` | `void`，提交阶段登记，effect 清理注销 |
| `/stores/zustand` | `registerZustandState(plus, store, idOrOptions)` | 幂等注销函数，RP dispose 兜底 |
| `/stores/redux` | `registerReduxState(plus, store, idOrOptions)` | 幂等注销函数，RP dispose 兜底 |
| `/stores/jotai` | `registerJotaiState(plus, store, atom, idOrOptions)` | 幂等注销函数，RP dispose 兜底 |

两个框架入口均允许省略登记参数，作为无登记的空操作，便于创建器始终委托同一入口；options 对象一旦提供就必须有 ID。直接接入已有状态是可选路径，不要求所有业务改回“创建后再登记”。普通组件仍优先使用 `useRp*`，Vue Options API 仍在 `setup()` 中使用同一套 composables。通用 Core 的 `registerStateBridge` 不因此恢复为业务公开接口。

本计划只涉及源码、类型、文档和验证。版本提升、npm 发布、站点部署与业务消费者迁移分别处理；本次评估不执行这些动作。

## 2. 源码核对与必须先修的边界

| 位置 | 当前事实 | 实施要求 |
| --- | --- | --- |
| `src/core/native-bindings.ts` | 已有统一 binding host、初值快照和 QS 归属校验 | 复用，不另建状态注册表；更新“应用不直接登记”的内部注释 |
| `src/react/native-state.ts` | 已有私有 `useBinding`，render 中写 `latest.current`、配置及初值候选 | 抽出公开 Hook，同时隔离未提交 render；不能只导出或改名 |
| `src/vue/native-state.ts` | ref 与 reactive 的桥接、scope 清理目前在创建器内部 | 抽出来源适配；先辨识原生来源，再辨识访问器 |
| `src/stores/native.ts` | 创建、来源登记、动作枚举与 Redux reducer 包装集中在一处 | 分离创建准备和登记；三个创建器实际调用各自公开登记函数 |
| `src/core/router.ts` 的 `bindGlobalSource` | 先写索引／规则，再建立订阅；失败前可能拿不到注销句柄 | 单来源登记也必须事务化；上层仅聚合 stop 不足以回滚 |
| `src/core/state.ts` 的 `registerBridge` | 先将 entry 放入 map，再调用 `subscribe` | 订阅抛错时撤销该 entry；保留已有取消和身份保护 |
| `src/stores/native.ts` 的 `actions` | 仅首次枚举动作，未聚合动作注销 | 明确固定动作名称范围；同名替换取最新，组注销包含所有动作 |
| Redux 创建包装 | 生成 reducer 分支，真实处理内部更新 action | 仅创建阶段保留；不能移植到任意已有 Store |
| Jotai 创建包装 | 只检查存在 `write` 就同时开放赋值和调用 | 将“原生命令写入”和“完整值赋值”分开判断 |
| `src/core/router.ts` 的 `dispose` | 逐个调用 stop，一个 stop 抛错可能阻断后续清理 | 聚合清理继续执行，诊断错误，不能留下其他来源 |

以上是源码审阅发现，不是本次运行测试的结果。现有回归记录可作为实现基线，不能替代新增入口的验证。

## 3. 来源与能力合同

### Vue

公开输入支持原生 ref／computed、reactive 容器、原生 readonly proxy，以及 `{ get, set? }` 访问器。按 `isRef → reactive/readonly proxy → 访问器` 识别，普通对象和普通值拒绝接入。原生业务对象即使有 `get`、`set` 字段，也不改变其来源类别。

- ref 读 `.value`；只有原生允许写入时才登记写能力。
- reactive object、Array、Map、Set 保留原代理身份；容器写入先处理别名和输入类型，不能清空正在作为输入的同一个 Map／Set。
- readonly 来源从登记能力上只读，不能先声称可写、到执行时才失败；也不能绑定需要恢复写入的 QS。
- 访问器 get 是纯读取，不承诺固定调用次数；按 `source.get()`／`source.set(next)` 调用，保留 receiver；`get` 必须可调用，提供的 `set` 必须可调用。setter 的业务校验与副作用仍由来源拥有。
- 访问器使用 Vue getter watch 追踪其实际响应式依赖。readonly(raw) 或普通外部对象没有响应式依赖时，不承诺原生能力之外的主动通知，不增加轮询。
- 保留现行作用域规则并写明边界：组件自身 effect scope 中的来源属于页面实例；其他 effect scope 中的来源属于当前 RP 实例，并随该 scope 清理。因此 Pinia setup store 和普通嵌套 effect scope 都按共享 scope 处理；这不是对 Pinia 或 Store 身份的自动识别。不增加依赖框架私有 Store 标记的判定。

`useVueState` 的来源识别、容器写入与只读判定集中为可阅读的适配清单；`useRpRef`、`useRpReactiveState`、`useRpComputedState` 仅负责原生创建、委托登记与返回。未传登记参数时跳过登记，不要求 Provider；Options API 不新增配置体系。

### React

`useReactState` 支持以下显式来源；普通值用 `{ get }` 表达，不增加自动猜测规则。

| 来源 | 识别与读写 |
| --- | --- |
| 原生 state tuple | 长度恰为 2，第二项为可调用的 React setter；赋值使用 `setter(() => next)`，支持函数值 |
| 可调用函数 | 登记调用能力；每次调用使用最后一次提交的函数 |
| ref 对象 | ref-like 对象的 `.current`；原生 ref 无可靠运行时品牌，不宣称可以鉴别对象的创建出处 |
| `{ get, set? }` | 显式访问器；getter-only 只读，提供 set 时按完整值调用 |

运行时分发顺序固定为 tuple、函数、ref-like、访问器；无效 tuple 或访问器在登记前拒绝。普通数组即使恰好符合 tuple 形状，也不得作为“普通值”传入；应包成 `{ get: () => array }`。函数只读值同样使用访问器，与可调用来源区分。

访问器的 `set` 是业务完整值写入，不自动套 React updater；例如函数类型 state 若采用访问器，应由适配器写成 `set: next => setHandler(() => next)`。使用原生 tuple 则由登记入口处理这一差别。

生命周期按以下顺序组织：

1. render 只构造来源候选和 owner 地址，不改登记表，不调用会创建 owner 记录的 `plus.scope()`，也不把候选闭包写入活跃桥可见的共享 ref。
2. commit 阶段解析实际 owner，发布已提交的 getter、setter、callback；初值只取首次成功提交的登记 render 的候选快照。
3. effect 阶段登记；首次读取 ref 保留原生 `.current` 的实际可见性，DOM ref 仍拒绝 QS。
4. 普通重渲染仅更新已提交访问器和通知；ID、owner 或能力集合变化时清理后重新登记。
5. Strict Mode、Suspense／废弃 render 和卸载都不能泄露候选来源、重复 ID 或订阅。取消已发出的业务写入不等于回滚原生副作用。

原生 ref 的直接读取始终最新；直接 `.current` 修改不保证即时通知。普通访问器也只观察本 Hook 的已提交重渲染，不假装订阅任意外部 Store。需要原生 Store 通知时使用对应 Store 登记入口。

`useRp*` 无条件调用 `useReactState`，登记参数省略时其内部无登记、无 RP 订阅、无需 Provider。配置按一次登记生命周期固定，原生值和闭包仍随 commit 更新。新增公开重载不能以 `any` 抹平 tuple setter、值类型或函数参数。

## 4. Store 的读取、调用与赋值分开

三个 Store 入口都使用已有 Store，参数顺序保持“RP、来源、配置”。返回的注销函数清理主来源、动作子来源、订阅和动态 QS 归属；共享 Store 不随使用它的页面卸载注销。

复用 `StateIdOrOptions<S>`。Redux、Jotai 的写适配采用各自的 options 扩展，形如 `{ id, set(next), ...导航配置 }`；字符串 ID 保持简写。`set` 在适配器中提取，不能流入通用字段导航规则或 Core 的业务判断。

### Zustand

支持 bound store 与 vanilla StoreApi。读取原生数据、使用原生 merge 写入、订阅原生通知；动作仍按 `ID/method` 索引，读取并调用时取得最新方法且保留 Store receiver。不得用 replace 写入快照而删除动作。

0.3.1 固定登记时的动作名称集合：同名函数替换立即使用新函数；移除或变为非函数时调用明确失败，不执行旧函数；后来新增的动作不自动进入索引。改变动作集合通过注销后重新登记完成。这里不增加另一套动态动作监听和重试协议。

创建器的流程固定为 `native create → registerZustandState → 返回原 Store`；原生泛型、middleware 与 currying 保留。

### Redux

`registerReduxState` 默认只读状态，并在 `ID/dispatch` 提供原生调用。需要赋值或 QS 恢复时，options 必须提供以完整 state 为输入的 `set(next)`，由业务适配分发已有 action。登记入口不调用 `replaceReducer`，不包装已存在的 reducer，不通过忽略未知 action 伪造写入成功。

`configureRpReduxStore` 保留创建阶段的便利：

- 未传登记参数时，只执行原生 configure。
- 提供业务 set 时，使用业务 set，不增加无用的内部 reducer 分支。
- 没有业务 set 时，在创建前准备现有的更新 reducer 和相应 writer；创建后将该 writer 作为显式适配传给 `registerReduxState`。

因此保留正常的 0.3.0 创建行为，同时直接登记已有 Store 时默认只读。两者能力差异在签名、示例和用例中说明，不靠 Core 猜测 reducer。

### Jotai

显式使用传入的 Store 与 atom，不另取默认 Store。

- 只读 atom：只读，无原生调用或赋值能力；不得配置 set 或恢复型 QS。
- WritableAtom：允许 `callState` 原样转发其参数元组到 `store.set`，保留同步／异步结果；这不自动授予 `setState`。
- 已有 WritableAtom 要赋值：提供 `set(next)` 适配，由业务将完整值转换为原生写入参数。
- 创建器只有在确定属于原生默认 primitive 构造分支时，才能自动提供完整值写适配；不能仅凭 `write` 字段推断。

primitive 判定依据创建参数和项目实际 Jotai 公开重载：纯初值构造与 `read`／自定义 `write` 构造分别覆盖，`atom(initial, customWrite)` 也不能当成默认赋值。明确的 `atom(undefined)` 初值仍可纳入；不新增歧义性的无参登记写法。派生、多参数、命令型与异步写入分别编写回归，不读取私有标记。

`createRpJotaiAtom` 准备好明确的 primitive writer 或调用方 writer 后，委托 `registerJotaiState`，返回原 atom。

## 5. Core 生命周期基础修正

沿用现有 binding host、PageStateBridge、scope 和 QS 引擎。公开适配器只把原生来源转换成已有通用能力，不让 Core 导入 React／Vue／Store 类型。

事务需要同时覆盖单来源和一个 Store 的登记组：

1. 先验证来源能力、ID、主来源／动作具体 ID 冲突和参数归属。
2. 暂存本次建立的索引、订阅及动态规则的精确清理句柄；订阅抛错也必须撤销已插入的 entry。
3. 批次完成前不发布半套动作或开始 QS 写回。即时订阅回调可读取原生来源，但地址同步在提交后统一启动。
4. 失败按相反顺序清理，只删除当前事务仍拥有的项，保留原有来源、静态页面声明与最初异常。
5. 注销先使整组失活，再解除动作和主来源；重复调用、RP 已 dispose 后调用均安全。清理异常不能阻断其他清理，分别进入诊断。
6. RP dispose 必须触发同一组清理，不能只清掉 map 后让聚合注销仍认为自己活跃；清理句柄不继续持有已结束的订阅和可释放来源。

这些是现有登记机制的生命周期修正，不新建注册总线、业务 Store 或通用工作流框架。异步写入继续使用已有作用域／entry 身份校验；实际已发出的业务 setter、dispatch、atom onMount／onUnmount 副作用不承诺可逆。

## 6. 类型与错误边界

- Vue ref／computed／reactive、React tuple／ref／callback／访问器分别保留重载，不把来源先变成普通值后推断。
- 读值、完整值赋值和原生命令写入是三个能力。自定义 computed 的读写类型不同时，不能用统一 S 掩盖差异；需要恢复完整值的 QS 应通过类型与显式访问器适配约束，不靠运行时猜测 setter 语义。
- Store 的 state 从 `getState`、atom 值与 `WritableAtom<Value, Args, Result>` 推导；公共注册签名拒绝不兼容的 set。
- `callState(id, ...args)` 保持现有动态 ID 的 CommandResult 合同。适配器和原生 API 保留 Args／Result，运行结果按现有 await 规则装入 CommandResult；不宣称仅凭字符串 ID 能获得全局静态返回类型。
- 来源形态的纯校验可以在登记前执行，不修改索引；重复 ID、缺少 owner 和只读 QS 等登记错误同步抛出，React 的登记错误发生在 effect 阶段。getter 本身的读取异常按实际发生阶段处理，不能承诺全部推迟到 effect。错误需有来源和阶段诊断，不能转成不匹配的容量／网络提示。
- 注销使未完成的操作失效；后续 getState／setState／callState 的未知来源行为沿用当前合同。只读不等于执行失败，命令型不等于可赋值。

## 7. 模块归属与实施顺序

| 步骤 | 修改位置与产出 | 完成条件 |
| --- | --- | --- |
| S1 生命周期 | `core/native-bindings.ts`、`core/state.ts`、`core/router.ts` | 单项与批次回滚、聚合清理、dispose、取消身份均有独立用例 |
| S2 Vue | 新增 Vue 来源适配模块，调整 `vue/native-state.ts`、`vue/index.ts` | useVueState 公开；三个创建器实际委托；原生身份不变 |
| S3 React | 新增 React 来源登记模块，调整 `react/native-state.ts`、`react/index.ts` | useReactState 公开；提交态隔离与固定 Hook 顺序成立 |
| S4 Stores | `stores/zustand.ts`、`stores/redux.ts`、`stores/jotai.ts` 及各自登记实现 | 三个 register 公开，创建器委托，能力差异可由同一路径验证 |
| S5 收敛编排 | 缩减 `stores/native.ts` | 只保留必要共用机制，不再同时拥有三套创建和登记逻辑 |
| S6 文档与公开面 | `docs/state-bindings.md`、`docs/frameworks.md`、README、文档站 `scripts/examples.mjs` | API 清单由来源生成，双语示例及所有导出一致 |

静态来源类别采用具名 handler 的集中适配清单；类型声明和运行判定相互验证。具体值解析、容器写入与订阅生命周期留在所属模块，不把清单做成旁路文档。批次清理只抽取三端共用的机制，不为五个公开名字另造一个调度框架。

每一步先完成其对应最小回归，再进入依赖它的步骤；包构建和完整回归集中在接口接线完成后执行，避免每改一个函数就重复编译全仓库。
