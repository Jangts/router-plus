# Router Plus 0.5.0 迭代计划：常见页面能力的完整接入

日期：2026-11-23。状态：库侧实现已落入本地 0.5.0，构建、回归、包体消费和文档生成通过；消费者迁移及实际应用验收未执行，未发布。实际交付与验证边界见[实施验收记录](0.5.0-implementation-acceptance-2026-11-23.md)。关联[状态绑定提案](2026-11-23-query-state-binding-proposal.md)。

## 1. 目标与证据范围

应用声明原生状态、默认值、参数归属及必要业务校验后，常见页面行为应完整工作。库负责地址恢复、变更同步、初始化、并发、取消和实例生命周期；App 不再维护另一套通用同步机制。是否简化以可以删除的消费者代码和完整场景证明，不以新增 API 数量衡量。

初始盘点只读 Cafe 与 WFJ Campaign Console 的现有源码，并对照 RP 0.4.6 的实现和测试源码；当时未运行应用或库检查。后续库侧实施与检查单列于实施验收记录。消费端报告刷新丢 Tab，具体应用运行时序仍未复现，不预判已修复其根因。

Cafe 根目录为 jangts/main，主要范围 apps/cafe/src；Console 根目录为 ripple/wfj-campaign-console，主要范围 apps/frontend/src。只将通用机制提炼成匿名需求，不复制消费者业务实现、权限规则或私有资料进入库。未改动两个消费者的源码。

## 3. 六项核心交付

### P01 — 单一声明完成 Tab／筛选原生绑定（P0）

复用 useVueState/useRp* 与已有页面 states，不建立另一份实时状态。原生初值、参数名、允许值与编码只决定一次。明确页面 states 是挂载前可用的路由合同，原生绑定是实际来源；重叠声明需有明确优先级、冲突诊断和省略方式，不能让 App 两次维护同一列表。

直接删除 Dashboard 的 URL 双向 watch、重复初读和 JSON 防循环；Cafe 的类型化业务包装可保留，但不再负责手动猜测通用恢复时序。不要强制所有 App 使用页面 states，也不要强制迁移已有 ref。

验收：带 query 首次访问／刷新、缺参、非法枚举、同页导航、前进后退、卸载重挂、保留页激活均符合相同合同；默认值不得先覆盖地址意图。正常使用不需要 App watch/同步锁/手动 whenReady 才能正确恢复。异步恢复在完成前如何向 UI 表达，需明确，不能用“最终会一致”替代。

### P02 — 异步校验就绪与恢复（P0）

当前 values 被登记快照化；validate 可以读取最新目录，但不存在目录就绪通知或自动重验合同。whenReady 仅表示 RP 的任务就绪，不是业务目录加载完成。因此库不能把“目录尚未取得”当成“值非法”。

在现有原生绑定上设计可观察的就绪／重验条件；具体 API 待接口评审。库统一保留待恢复地址、延迟依赖目录的校验和回写、就绪后重验、处理过期导航及卸载，不要求 App 重新注册来源或复制一套 pending 状态。

App 提供目录、合法性判断及合法缺省值，拥有加载失败、权限变化和空目录的业务含义。必须区分未加载、加载失败、成功但为空、当前值无权限四种情况。待就绪期间用户新选择、浏览器遍历和旧请求迟到的优先级应明确。

验收：Tab 目录、版本目录、阅读章节三种来源；加载前保留合法深链，失败不清空 URL，就绪只应用最新地址，离页不写新页面，手动选择不被旧恢复覆盖。路径参数场景先验证可复用接入，未经必要性证明不扩张 query 配置。

### P03 — 历史策略与地址提交协调（P0）

现有原生绑定经 navigateState 固定 replace；pendingStateValues 已负责部分并发合并，不重写一套队列。补充绑定层可声明的 push/replace 行为，明确默认值保持兼容；普通筛选 replace、需要历史的 Tab push 可分别选择。多字段一次更新不能制造中间历史项。

统一规定来源变化、快速连续变化、跨绑定合并、外部导航、取消与卸载的处理；query 与 history state/hash 必须保留无关部分。历史策略和模型回执不得冲突。

验收：两个绑定同轮更新、连续输入、Tab 与筛选同时改变、后退遇到未完成写入、守卫拒绝／重定向、组件卸载；无丢参、回环、幽灵提交。防抖仅作为需证据支撑的候选，不默认新增计时器；如采用需定义 flush/cancel，不静默丢最后一次输入。

### P04 — 编解码、缺省与局部参数更新（P1）

沿用已有 codec、字段投影与参数所有权，收敛消费者的 queryText、逐键补丁、删参、相等判断和默认参数省略。默认值是否省略、空串/null/undefined/缺参的意义分别明确；不得把不相等的业务值合并。URL、已有 history、本机偏好和原生缺省的优先级须显式，避免用当前本机值误吞 URL。

内置基础值处理；逗号数组、日期、版本号到 ID 和业务 filter 结构由 App 的 codec／校验提供，不把商品字段或阅读协议写入 RP。不以提供复杂 schema DSL 代替已有回调。评估是否需要 query 局部更新入口；已有编码机制可满足时优先补完整组合示例。

验收：空值、false、0、数组／重复参数、对象、非法 JSON、日期 codec、旧缺省参数、省略后重新进入、多个绑定共存与默认回退。不支持的输入有诊断且不泄露未绑定状态。

### P05 — 声明保留页面与宿主生命周期（P1）

现有 React RouterPlusView/Retained/Scope 与 Vue View 已有保留能力。先用真实 Cafe 路由形状验证能否删除自建 visits、location/context 冻结、release 订阅和 generation；能覆盖就接入现有入口，不另造 KeepAlive。

确有不足时，在既有 host/retention 合同上补自定义渲染宿主适配，让 React Activity、Vue 缓存和自定义页面壳只声明如何展示／隐藏，缓存身份、scope、释放与重新进入由库管理。不能把 Cafe 的页面滚动容器、视觉或固定路由列表搬入包。

验收：列表到详情再返回、同一路径多个参数实例、隐藏实例不接收其他页地址、主动 release 后重建、淘汰、StrictMode、Vue 卸载及 host 清理。Activity 隐藏与普通 hidden 的 effect 行为不同，应独立验证，不能只验 DOM 还在。

### P06 — 原生导航目标与安全策略的接入简化（P1，先审计）

对照 Cafe 和 WFJ 的目标包装与 RP 既有 resolve/Link/Redirect/协议插件。列出可直接删除、需要可选策略和必须保留的每条规则。通用部分包括 query-only/hash-only 目标、相对地址、basename、同源/外链、安全协议与含凭据目标的判断。App 仍决定其路由白名单、自定义协议、权限和动作语义。

已有能力通过最小接入示例解决；真实缺口才增加可选配置，不改变合法地址默认解释，也不默认禁止其他应用需要的相对路径。Vue named route／params 目标若需支持，通过原生适配器或显式转换实现，不让 Core 依赖 Vue 类型；是否新增公开入口以减少真实包装为准。

验收：两端目标矩阵包含完整URL、站内路径、相对路径、?query、#hash、同源绝对URL、basename、未知路由、危险协议、凭据地址，以及 no-op/拒绝/取消的真实回执。业务状态分类不替代原始 CommandResult。

## 4. 三项接入清理与验收，不算新增通用框架

- D01 声明与兼容：Cafe useRouterProTab、useRouterProSearchParams 和 WFJ 页面目录各给最小迁移示例；保留真实业务类型映射，消除默认值与合法值的重复维护。确认 usePageQuery 函数更新是否读取最新提交基线；当前 React 闭包 params、Vue computed 当前值的差异应通过并发用例判定，不预先定性为故障。
- D02 装配与存活期：核对 Cafe 手工 initialLocation、history key 适配、attachGlobal、StrictMode 代际清理与 WFJ applicationRuntime/HMR 包装。历史数据迁移与应用级热更新策略仍归 App；库生命周期重复补丁需优先吸收。只移除被证明由包承担的保护。
- D03 路由状态触发业务与守卫：给初次和后续参数变化的同一消费路径，以及 existing execute/callState 的就绪、取消、回执示例。异步任务在 App 中执行；避免首次 onMounted 与 watcher 重复触发。未保存编辑、权限与启动守卫沿用实际原生路由，验证库发起的导航、后退和 query 变化均经过正确检查，不增加表单事务引擎。

## 5. 最小接入与可删除代码的验收要求

静态场景的基线使用现有能力，不是新 API 承诺：

```ts
// Vue 页面 setup，父级已安装 createVueRouterPlus({ router, pages })。
const tab = useRpRef('overview', {
  id: 'tab', query: true, values: ['overview', 'products'],
});
const filters = useRpReactiveState(
  { keyword: '', category: 'all', page: 1 },
  { id: 'filters', query: true,
    fields: { page: { validate: value => typeof value === 'number' && Number.isInteger(value) && value > 0 } } },
);
```

实际应用保留各自 Tab 清单、业务默认与校验。0.5 必须补对应 React 示例、已有 ref 的 useVueState 示例，以及不写 watch 的异步目录与历史策略示例；未评审的新配置不在本文伪装成可用 API。

成功不能只看示例运行：迁移前后列出保留和删除的函数，特别是 Dashboard 的 readFilters/buildQuery/双向同步（业务 codec 部分保留）、Master replaceQuery 的机械部分、版本页加载期间同步禁令的机制部分、Cafe 保留页缓存和纯装配重复。业务加载 watch 不以减少 watch 数量为由删除。

## 6. 实施顺序、兼容与完成标准

1. 固定消费端报告的复现与证据，建立首屏／刷新／历史遍历的基线；先判断漏接与时序，不能通过放宽断言使刷新问题“通过”。
2. 评审 P01—P04 的合同，优先复用原生绑定；完成静态／异步两个最小示例，再实现实际缺口。
3. P05/P06 先用现有公开 API 完成接入审计，证明不足再增补；同步处理 D01—D03。
4. 同一最终 tarball 在隔离消费目录验证 React/Vue 的类型、运行、示例和文档。再分别在两个 App 验证受影响场景，不拿源码别名运行替代包体验收。

0.4.6 的正常绑定默认继续 replace；codec、URL 含义、PageDefinition 与原生 source 身份保持。若决定改变默认值省略或地址解释，单列破坏性变化和迁移，不借 0.x 版本静默改变行为。创建 hook 和已有来源绑定必须共用一份运行机制；禁止新建平行 query store、同步锁框架或应用状态副本。

每项结果归入：消费端漏接／文档缺口／易用性不足／已复现运行时缺陷。完成标准是消费者只提供业务声明即可通过场景，通用同步和生命周期补丁可删除，包体与消费者证据明确。压力测试、UI 外观、线上部署与 npm 发布不在本计划执行范围；视觉验收归用户，运行与发布另按授权。
