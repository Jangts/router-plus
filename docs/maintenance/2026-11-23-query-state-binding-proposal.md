# 提案：常见页面状态与 URL 的低成本声明式绑定

日期：2026-11-23。状态：待评估，不构成实施或发布授权。

本提案已纳入 [0.5.0 迭代计划](0.5.0-iteration-plan.md)，与 Cafe 和 WFJ Campaign Console 的其他通用封装一并评估；运行时根因仍以复现证据判定。

## 背景与证据边界

WFJ Campaign Console 使用 @jangts/router-plus 0.4.6。用户报告 `/dashboard?tab=products` 刷新后回到默认 Tab。消费端只登记页面，Tab 和筛选使用手写 ref、watch、router.replace；原代码仅初始化读取 query，缺少后续路由恢复监听。消费端已补同步，但没有运行复现刷新时序，因此尚不能认定 Router Plus 有运行时缺陷，也不能把这一代码缺口视为完整根因。

0.4.6 文档已有页面 states 的 default/values/query 配置，以及 useVueState、useRp* 的 query 绑定。本提案不预设新增 API，应先判断现有能力是否足够简单、完整。

## 用户要求

仅有底层能力不够。Tab、筛选条件与 URL 同步属于常见需求，应由应用声明状态、默认值、允许值和参数绑定后直接工作。如果应用仍需多组 watch、同步锁、防循环或特殊初始化顺序，公共包的封装职责仍未完成。不能仅以消费者没有正确接入为由排除框架易用性问题。

## 请评估

1. 首次打开、整页刷新能否从 URL 恢复原生状态，避免默认值提前覆盖 URL。
2. 前进、后退、同页导航及保留页面重新激活是否一致。
3. URL 写入的 replace/push 策略、快速连续更新是否可靠。
4. 默认值、非法枚举、空值、布尔、数组、自定义日期的编解码；只修改归属参数，保留其他 query 和 hash。
5. 异步目录与选项未就绪时，如何避免误判合法状态并重置。权限与业务合法性仍由应用负责。
6. 页面 states 声明与原生状态绑定各自职责、是否重复配置；Vue 与 React 的能力和接入成本是否一致。

## 预期评估结果

- 优先用现有 API 给出最小可用 Vue 示例，覆盖 Tab 和一组筛选；明确消费端应删除哪些手写同步代码。
- 区分消费者漏接、文档不足、配置繁琐和运行时缺陷，给出证据。
- 现有 API 已足够时补足可发现的示例；不够时提出最小改进方案，复用既有原生状态绑定，不建立第二份实时状态。
- 给出建议方案、兼容性影响和最小验证范围。先评估，不直接改实现、发布或迁移消费端。
