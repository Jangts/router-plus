# 日志规范

本规范约束本项目的诊断、错误、构建输出及可选运行日志。具体事件、存储格式、开关、根目录、保留期和查看方式由所属模块声明；库的诊断回调、内存记录与应用持久化日志分别维护，不统一要求文件库、日志数据库或后台采集。

## 所有权与执行事实

- 产生事件的模块负责事件含义、阶段、错误分类及真实执行身份；宿主负责接收、存储、披露和保留。通用库不导入应用日志实现。
- 可枚举事件及允许字段通过实际参与执行的清单管理，调用点消费同一声明。跨模块关系记录真实父子与调用身份，不把日志投影当作一次新执行。
- 明确区分可信程序事实、第三方返回和客户端报告。记录发生了什么及失败位置，不根据缺少日志推断完成。
- 不整体序列化服务实例、运行配置、浏览器存储或任意请求；仅构造声明范围内的记录。

## 内容与隐私

采集策略先于正文构造和排队。关闭或省略正文时不创建临时原文；metadata 模式只保留声明的技术字段。错误消息和堆栈也可能包含正文或秘密，按同一策略处理。

Authorization、Cookie、密码、API key、访问令牌、签名密钥及已知秘密值在输出前保护；错误、响应与附件采用同一边界。普通姓名、日期和引文不作为粗糙的关键词黑名单删除。采集业务正文须有所属产品的明确规则，不因排障默认扩大记录范围。

用户可见错误与内部诊断分开。适用的界面提示按普通使用者书写；内部保留可分析的错误分类、技术消息、阶段、堆栈及限额名称、允许值与实际值，并继续服从记录开关和内容保护。

日志不自动成为业务数据、事实依据、授权、知识来源、模型上下文或外部平台上传内容。它与问答、画像、业务回执及长期审计分别遵守自身生命周期。

## 可靠性与资源

队列、内存记录、附件、输出大小及保留时间有明确界限；溢出、丢失、截断和未完成状态如实表达。记录失败不替换原始业务错误，不额外重试副作用、不重复调用外部服务；观察回调和诊断 sink 的失败按所属合同隔离。

需要持久化时，由所属实现明确并发写入、原子替换、崩溃恢复、损坏记录及完整性验证方式；只承诺已经实现的可靠性。访问或查看不自行延长保留时间。清理限定自身记录，保留业务数据、OSS、备份、内容原件与外部工程。

运行日志、临时诊断及凭据排除于 Git 和发布包。目录与文件权限按内容敏感性设置，生产持久化位置由部署配置明确，不借用源码目录或镜像层保存长期日志。

## 验证与使用入口

按真实疑问检查失败传播、取消、迟到结果、回调隔离、记录容量、隐私和清理范围。内存回归不证明持久恢复，本机模拟不证明线上日志已正确配置。记录实际开关、数据来源与未验证边界。

本项目的实际诊断与验证入口见[项目检查入口](review-entrypoints.md)；执行频率、视觉查看与外部操作继续遵守[协作约定](../AGENTS.md)。
